## 目标实现

### 刷新与取信

- 显式健康检查/定时刷新中的 Graph Token 请求先用 Graph .default，再尝试省略 scope 的原始授权请求。若第一次已经取得可用 access_token，回退的超时、错误响应或无效响应不推翻已有成功结果。
- 普通 Graph 取信和注册验证继续使用已有的取信权限候选；进程内缓存成功端点与 scope，最多 2048 项。缓存键使用 client_id 与 Refresh Token 的 SHA-256 摘要，不存放明文令牌；新旧令牌分别登记，重新导入不同凭据不会命中旧缓存。
- 权限相关错误才继续同一端点的 Graph scope 回退；失效凭据不再穷举该端点的所有 scope；429 和服务端错误立即返回临时不可用。
- 仅接受非空字符串 refresh_token；未返回、空值、无效类型、新旧相同时继续保留原值。
- 刷新任务取得新 Token 后必须写入成功才报告成功。磁盘失败、账号已删除或凭据已被并发修改时，保留原有数据并报告失败。
- 普通取信遇到轮换写回冲突时，仍可使用此次取得的 access_token，但不会将这次写回标为成功。
- 注册验证发生轮换时，将新令牌保存在当前请求凭证中，注册成功时统一落盘，避免再次写回旧令牌。

### 记录与展示

账户列表和健康结果新增：

| 字段 | 含义 |
| --- | --- |
| refresh_status | 本次 Token 刷新结果，success / failed；旧记录为 null |
| token_rotated | 本次是否真正更新；旧记录为 null |
| refresh_message | 验证成功未轮换、已更新或失败说明 |
| last_refresh_at | 最近一次刷新尝试时间 |
| last_refresh_success_at | 最近一次刷新成功时间，失败不会清除 |
| refresh_token_updated_at | 最近一次 Token 实际更新时间，未轮换不会更新 |

轮换时间同时写入 accounts.json；健康检查结果存储在已有 account_health.json 中。无需独立数据迁移，旧记录继续读取，未知的轮换与时间信息显示为未记录。

Token 刷新页按独立的刷新结果显示状态，另行显示邮箱健康结果。OAuth 成功但 IMAP/Graph 探活失败时，健康分仍按原有规则计算，刷新结果不会误报为 OAuth 失败。三类时间按浏览器本地时区显示；旧任务快照不能覆盖更新的结果。

### 调度退出修复

回归验证发现既有调度循环在事件唤醒与取消同时发生时可能无法退出（修改前测试同样挂起）。将 asyncio.wait_for(event.wait()) 改为 Python 3.11 的 asyncio.timeout 上下文，直接等待事件，使取消能够传播。项目 Docker 基础运行时为 Python 3.11。

## 2026-11-09 并发与停止缺陷修复

后续审查复现了旧导入覆盖新 Token、旧结果覆盖新状态/时间以及停止入口无效的问题，本次补充修复：

- 账号凭据保存和轮换保存均校验客户端所读取的凭据版本。导入验证开始时记录快照，保存前发现版本变化返回 HTTP 409，要求重新加载后提交。管理员主动重新导入仍可正常保存；删除后的旧请求无法重建账号。旧账号数据可直接读取，新保存时写入 credential_revision。
- 每次健康检查分配 refresh_sequence，持久化结果按发起顺序决定是否接受；API 列表和前端快照合并使用同一序号。请求完成时凭据已经变化则不写入旧结果。最近成功和轮换时间取有效时间的较晚值。
- 新增 POST /accounts/health-check/stop，沿用管理员/API Key 认证；可携带 task_id，旧页面不能误停不同任务。停止采用协作方式，当前账号完成刷新与保存后才跳过剩余账号。
- 后台任务返回 stop_requested / stopped；前端重试也会在当前请求完成后停止。停止按钮可见并能显示等待状态；部分完成不会显示为全量 100%。被停止的定时任务推进下一次计划，避免立即再次执行。

运行时仍沿用目标项目单进程/单 worker 的约束；文件锁和后台任务状态不提供跨进程协调。

新增回归文件：tests/test_token_refresh_concurrency.py、tests/test_token_refresh_stop.cjs。原审查复现脚本保留在 outputs/token-refresh-audit-2026-11-09/；导入竞态用例现在允许并要求返回 409，验证新 Token 不被覆盖。

## 失败后实时取信复核策略

- 首次 Token 刷新失败或 OAuth 成功但邮箱探活失败时，系统绕过邮件缓存进行一次实时收件箱读取：Graph 请求消息列表；IMAP 使用新连接打开 INBOX 并读取最新邮件头。空收件箱仍算读取成功；文件夹拒绝、读取失败、协议响应无效或网络异常都算失败。
- 实时取信成功后只重试一次 Token 刷新。成功则恢复健康；若第二次刷新仍失败，标记为“邮件可读取，但 Token 重试失败”。当前流程结束，后续仍可按原计划再试，不无限重试，也不直接判定邮箱失效。
- 实时取信失败后，账号持久化为“失效邮箱，待人工检查”，保存首次失败与取信复核错误。全量、定时和普通批量重试会跳过该账号，继续处理其他账号。
- 账户管理的单账号按钮发送显式 recheck: true。已暂停账号只有在实时取信和 Token 重试均成功后才恢复；旧页面或普通批量重试不能绕过暂停。
- 对错误描述中的 Account security interrupt for collecting proof / compromised，保留诊断并提示人工安全检查；不会仅凭 AADSTS70000 就反复尝试所有 scope。
- IMAP 健康检查验证 NOOP 返回状态。取信复核独立创建连接，不使用旧连接或本地缓存作为账号仍可用的证据。连接创建使用局部超时并清理认证失败的连接。

### 操作与兼容

后台由“待人工检查”计数和状态列出暂停账号；账户管理显示失败原因和“复检并恢复刷新”按钮。查看邮件功能保持可用。暂停状态存于已有健康记录，重启后仍生效，无需手工迁移。

按照本次策略，临时网络故障若同时导致实时取信失败，也会暂停该账号等待人工检查；诊断保留网络错误，不直接宣称账号永久失效。
